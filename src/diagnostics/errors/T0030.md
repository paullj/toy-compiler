# T0030: field blocks structural `Hash` derive

Calling `.hash()` on a struct or enum with NO explicit `Hash` impl tries to derive
one structurally: a struct conforms to `Hash` when EVERY field's type conforms to
`Hash` (recursively), and an enum conforms when every variant's payload fields
conform. The builtin scalars (`int`/`bool`/`str`/`unit`) always conform, so an
all-scalar struct derives `Hash` for free — no impl needed. The derived hash is
`Eq`-consistent (equal values hash equal) and uses a fixed seed, so it is
reproducible run-to-run.

The derive fires only when it can. If a field's type does NOT conform to `Hash`, the
struct cannot derive it, and the call reports the FIRST offending field by name:

```
enum Color { R(int), G, B }
impl Color has Eq { fn eq(self, o: Color) -> bool { true } }
struct Bad { c: Color }   // Color has no `Hash` conformance

fn main() -> int {
    a := Bad{ c: Color.G }
    return a.hash()
    // error: cannot derive 'Hash' for 'Bad': field 'c' of type 'Color' does not conform to 'Hash'
}
```

Two fixes:

- Make the offending field's type conform. Give it its own `Hash` impl, or let it
  derive structurally by making ITS fields conform.
- Or give the OUTER type an explicit `impl Bad has Hash { fn hash(self) -> int { .. } }`,
  which overrides the derive entirely (an explicit impl always wins over the derive).
  If you do, keep it `Eq`-consistent: values that compare equal must hash equal.

The derive is lazy: an unused type synthesizes no code. It only runs at a `.hash()`
use site, which is where this error surfaces.
