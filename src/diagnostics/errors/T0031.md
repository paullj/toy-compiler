# T0031: value does not conform to `Display`

`print(x)` accepts ANY value whose type conforms to the prelude `Display` protocol.
`Display.display(self) -> str` builds the value's rendering as a `str`; `print(x)` writes
that str (`print(x) == write(x.display())`) and `to_string(x)` returns it, so the same
error gates both. The
builtin scalars (`int`/`bool`/`str`/`unit`) always conform, and a struct or enum with
NO explicit `impl` derives `Display` structurally when EVERY field's type conforms
(recursively). So `print("hi")`, `print(42)`, and `print(P{ x: 4, y: 2 })` all work
with no `impl` in sight.

The derive fires only when it can. If a field's type does NOT conform to `Display`,
the struct cannot derive it, and the `print` call reports the FIRST offending field by
name:

```
enum Color { R(int), G, B }
impl Color has Eq { fn eq(self, o: Color) -> bool { true } }
struct Bad { c: Color }   // Color has no `Display` conformance

fn main() {
    print(Bad{ c: Color.G })
    // error: cannot 'print' a 'Bad': field 'c' of type 'Color' does not conform to 'Display'
}
```

It also surfaces on a generic parameter with no `Display` bound, because the compiler
cannot know the concrete type conforms:

```
fn show[T](x: T) {
    print(x)   // error: cannot 'print' a value of type 'T': it does not conform to 'Display'
}
```

Two fixes:

- Add a `Display` bound to the generic parameter (`fn show[T has Display](x: T)`), or
  make the offending field's type conform (give it its own `impl`, or let it derive
  structurally by making ITS fields conform).
- Or give the type an explicit `impl Bad has Display { fn display(self) -> str { .. } }`,
  which overrides the derive entirely (an explicit impl always wins). The method
  returns the rendering as a `str`.

The derive is lazy: an unused type synthesizes no code. It only runs at a `print` use
site, which is where this error surfaces.
