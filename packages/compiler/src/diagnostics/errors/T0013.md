# T0013: generic form not supported yet

The type checker gives generic code its meaning, but a few generic forms are not
supported yet; each is rejected here.

- A method of a builtin type with type parameters of its own (below).
- A generic tuple struct, `struct Pair[T](T, T)`; use a struct with named fields.
- An `impl` on one instance of a generic type, inherent (`impl Box[int] { .. }`) or a
  conformance (`impl Box[int] has Into[int] { .. }`), or one whose pattern is partly
  concrete or repeats a name (`impl Pair[T, int]`, `impl Pair[T, T]`); write
  `impl Box[T]`, naming each type parameter once, for every instance. This is the
  impl's only error: its methods are not checked against the protocol, and neither a
  call of one nor a bound it would have met reports anything more.
- A generic protocol given a composite argument, `impl L has Conv[fn() -> int]` or
  `Conv[Vec[int]]`; its arguments must be plain value types. This too is the impl's
  only error.
- A generic call whose callee is no name (`fs[0](1)` of a generic function) needs
  explicit type arguments.

## Methods

A method of a struct or enum, generic or not, may declare type parameters of its own
(`impl P { fn conv[U](self, f: fn(int) -> U) -> U }`), inferred at each call. A method
of a builtin type cannot yet: it is rejected at its declaration, and a call of it reports
nothing more.

```
impl int {
    fn conv[U](self, f: fn(int) -> U) -> U { f(self) }  // error: 'conv' declares its own type parameters
}
```

Make the method a generic fn (`fn conv[U](n: int, f: fn(int) -> U) -> U`), or drop
its type parameters.
