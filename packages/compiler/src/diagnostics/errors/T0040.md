# T0040: argument type mismatch

An argument's type is not assignable to the parameter it is passed for. The
diagnostic names the position, the expected and actual types, and the callee's
full parameter-type signature, with a secondary label at the definition.

```
fn takes_int(a: int) -> int { return a }

takes_int("hi")   // error: argument 1: expected int, got str; 'takes_int' takes (int)
```

In a pipe, the piped value is argument 1:

```
"hi" |> takes_int   // error: argument 1 (the piped value): expected int, got str; ...
```

Fixes:

- Pass a value whose type matches the parameter.
- Follow the "defined here" label to the definition to see the parameters.

In a pipe with a `_`, the piped value is the `_`'s argument:

```
"hi" |> add(1, _)   // error: argument 2 (the piped value): expected int, got str; ...
```

A `_` makes its own call a function, so a capture passed where a value is wanted is a
mismatch, and the message says so:

```
neg(add(1, _))      // error: argument 1: expected int, got fn(int) -> int; 'neg' takes (int);
                    //        its '_' makes it a function, so ...
```

The `_` captures only `add`'s call. To negate the sum, write the lambda around the outer
call: `fn(v: int) { neg(add(1, v)) }`. A tuple variant or tuple struct given a capture
(`Shape.circle(add(1, _))`) reports its own mismatch with the same hint.

A positional constructor value is an argument too: `Pair(1, 2)` for `struct Pair(int,
str)` is "tuple struct 'Pair': expected str, got int", and `Shape.circle("r")` is
"variant 'Shape.circle': expected int, got str". So is the argument of a compiler
intrinsic of the wrong type (`panic` takes a `str`).
