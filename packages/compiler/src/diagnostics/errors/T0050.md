# T0050: cannot infer a lambda parameter's type

A lambda parameter has no type annotation, and nothing around the lambda says
what its type is. A lambda takes its parameter types from the function type
expected where it is written: an annotated binding, a parameter of a known
function, a return position, a struct field or a `Vec` element. Without one,
every parameter needs a `: T`.

In a generic call a lambda is checked after the call's other arguments, against
what they bind, so `apply(fn(x) { x * 7 }, 1)` types `x` as `int`. Only when nothing
else in the call fixes the type variable does the parameter stay untyped:

```
fn apply1[T](f: fn(T) -> T) -> int { 0 }

fn main() -> int {
    g := fn(x) { x + 1 }       // error: nothing expects a function type here
    return apply1(fn(x) { x }) // error: nothing else in the generic call fixes T
}
```

A lambda passed to a call that is already an error (a method that does not exist, a
wrong argument count) gets no T0050: with no callee to type it, its parameters are
left for that error's fix.

Fixes:

- Annotate the parameter: `fn(x: int) { x + 1 }`.
- Or give the binding a function type: `g: fn(int) -> int = fn(x) { x + 1 }`.

## `_` captures

A `_` capture takes its parameter type from the function type expected where it is
written, else from the call it wraps: `add(1, _)` takes the type `add` wants at the `_`.
A generic callee gives it what the call's other arguments bind, so `pair(1, _)` is
`fn(int) -> int`. When no other argument binds the type variable, the callee reports it
(T0016), and the `_` adds no second error:

```
fn pair[T](a: T, b: T) -> T { a }
fn id[T](a: T) -> T { a }

fn main() -> int {
    f := pair(1, _)          // ok: fn(int) -> int
    g := id(_)               // error (T0016): cannot infer type parameter 'T'
    return f(2)
}
```

Write the type arguments, as in `id[int](_)`, or a typed lambda,
`fn(v: int) { id(v) }`.
