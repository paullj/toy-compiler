# T0039: arity mismatch

A function or method call passes the wrong number of arguments, or a lambda takes
a different number of parameters than the function type expected for it. For a
call, the diagnostic renders the callee's parameter-type signature and points a
secondary label at the definition, so the shape it expects is visible at the call
site.

```
fn add(a: int, b: int) -> int { return a + b }

add(1)   // error: expected 2 argument(s), got 1; 'add' takes (int, int)
```

In a pipe, the piped value is the first argument, so it counts:

```
1 |> add       // error: expected 2 argument(s), got 1 (the piped value is argument 1); ...
1 |> add(2)    // right: add(1, 2)
```

A lambda written where a function type is expected must take as many
parameters as that type. Its parameter types come from the expected type, so
a mismatch is reported at the lambda, not at the call:

```
fn apply(f: fn(int) -> int) -> int { f(1) }

apply(fn(a, b) { a })   // error: lambda takes 2 parameter(s), but the expected type fn(int) -> int takes 1
```

A constructor counts its values the same way: a tuple struct `Pair(1)` or a tuple
variant `Shape.circle(1, 2)` given the wrong number ("tuple struct 'Pair' expects 2
value(s), got 1"), and a compiler intrinsic given the wrong number of value arguments.

Fixes:

- Pass exactly as many arguments as the signature lists, or give a lambda as many
  parameters as the function type it is passed as.
- Follow the "defined here" label to the definition to see the parameters.
