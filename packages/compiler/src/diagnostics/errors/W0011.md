# W0011: method shadows a std or built-in method

A method the program declares has the name of a method that a bundled std module
declares on the same type, such as an `impl Vec[T] { fn each .. }` next to `std/vec`'s own
`each`, or the name of a method the compiler builds in for a builtin type, such as an
`impl str { fn len .. }`.

```
import std/vec

impl Vec[T] {
    fn each(self, f: fn(T)) { .. }   # W0011: method 'each' on 'Vec' shadows the one in std/vec
}

impl str {
    fn len(self) -> int { .. }       # W0011: method 'len' on 'str' shadows the built-in one
}
```

The builtins are `str`'s `len`, `byte_at`, `concat` and `to_string`; `eq`, `hash` and
`to_string` on the scalars; `into` and `try_into` on the numbers and `char`; and the
native `Option`/`Result` methods (`is_some`, `is_none`, `is_ok`, `is_err`, `unwrap`,
`unwrap_or`). A `to_string` or `hash` on the program's own type is how that type
implements them, so it shadows nothing.

This is not an error. In the program, the program's method wins: every call of that name
on that type that the program writes reaches it, whatever the import order. Calls written
inside std and core keep std's own method or the builtin, so a program's method never
changes what a std method does: `"abc".trim()` measures the string with the builtin
`len` even when the program declares its own.

The std-method case fires only when the std module is part of the program, imported
directly or through another module (`std/set` brings in `std/map`, which brings in
`std/vec`), because only then is there a std method to shadow. The builtin case fires
whatever the imports. The warning sits on the program's method declaration and names the
type, the method and the std module.

Rename the method (`each_back`, say) to keep both: calls of `each` then reach std's,
and the program calls its own by the new name. If the shadowing is intended, `--allow
W0011` silences it. This is a warning, so it does not fail the build; `--deny-warnings`
promotes it (and every warning) to an error.
